# 구독 AI 작성 흐름과 데이터 계약

## 목표와 모드

기본 모드는 ‘구독 AI에서 작성’이다. 상단의 ‘API로 작성’ 버튼은 비활성화한다. 기존 API 생성·모델·키 관리 코드는 향후 재활성화를 위해 보존하되 기본 화면에서 AI 호출을 자동 실행하지 않는다. 외부 AI 서비스의 구독·한도는 해당 서비스에서 처리하며 우리 서버는 구독 자격이나 남은 사용량을 조회하지 않는다.

웹 입력 → 임시저장·요청문 준비 → 사용자 직접 AI 웹사이트에서 생성 → JSON 가져오기·검증·저장 → 같은 문서의 미리보기 → 기존 확장 프로그램 전송 순서다. 외부 AI 사이트 조작·로그인 자동화와 일반 텍스트·HTML 가져오기는 이번 범위에서 제외한다.

## 입력과 요청문

- `topic`: 전체 글의 주제·흐름·구성과 구체적인 작성 요청이다.
- `place`: 글에서 다루는 장소다.
- `examples`: 말투·문장 길이·문단 구성·강조 방식에 대한 사용자 스타일 요구다.
- `images`: 저장된 이미지 ID, 사진 번호, 원본 파일명, AI 첨부용 파일명, 사용자 사진 설명을 제공한다. 카테고리·장소와 연관 지어 배치한다. 요청 준비 후 표시되는 사진을 내려받아 AI 웹사이트에 직접 첨부해야 한다. 내려받은 파일명과 요청문의 `filename`을 맞추며 첨부 순서나 UUID만으로 사진을 추측하지 않는다.

사진 번호·설명 입력·첨부용 다운로드는 ‘구독 AI에서 작성’ 모드에만 적용한다. API 모드의 기존 이미지 UI와 프롬프트 계약은 유지한다. 원본 파일명이 없는 이전 사진은 복원된 이름으로 표시하지 않으며 썸네일·설명과 새 다운로드 파일명으로 구분한다. 압축된 사진의 다운로드 확장자는 실제 이미지 형식에 맞춘다. 설명·순서는 이미지 URL 메타데이터로 보존하며 새 DB 컬럼을 요구하지 않는다.

사진 압축 중에는 요청 준비·임시저장·이전 결과 가져오기를 막는다. 입력 초기화·글 불러오기·계정 변경 시 진행 중이던 사진 처리 결과는 폐기한다. 일반 임시저장도 수동 모드에서는 사진 순서 메타데이터를 기록해 불러오기 후 순서를 유지한다.

요청문은 기존 공통 작성 규칙을 공유한다. 본문 최소 4,000자·가능하면 6,000자 이상, 이미지당 최소 두 설명 문단을 요청한다. 확인되지 않은 사실이나 반복으로 분량을 채우지 않는다. 글자 수·실제 내용의 품질은 사용자가 미리보기에서 확인하며 구조 검증 성공만으로 품질 준수를 보장하지 않는다.

수동 작성 요청은 한 문장을 짧은 paragraph로 나누고 3~4개마다 빈 paragraph를 넣어 문단 호흡을 끊도록 안내한다. 이미지 설명은 최소 두 문단을 유지하며 2~4개 문장으로 묶는다. 화면 자동 줄바꿈에 따른 실제 줄 수는 보장하지 않으며 text 내부 줄바꿈이나 공백 채우기를 사용하지 않는다. 전체 분량은 유지하되 장문·중복 표현을 줄인다.

이미지 한 장의 설명은 앞뒤 설명을 합쳐 최대 10줄(비어 있지 않은 paragraph 10개)로 제한한다. 최소 두 줄은 유지하며 빈 줄·화면 자동 줄바꿈은 세지 않는다. 최대치까지 분량을 채우거나 긴 문장으로 제한을 우회하지 않도록 요청한다. 이는 생성 프롬프트의 지침이며 서버의 저장 거부 조건은 아니다.

맛집·카페·여행의 첨부 사진은 단순한 대상 나열 대신 근거와 감상을 연결한다. 음식·음료는 보이는 특징을 맛·식감의 인상과 먹음직스러움에 연결하고, 공간·풍경·사물은 전체 분위기와 다양한 외적인 장점·근거 있는 아쉬움을 서술한다. 사진만으로 실제 맛이나 장소 전체의 시설 부재를 단정하지 않는다. 사진마다 표현을 다양하게 쓰고 사용자 예시 문장을 그대로 복사하지 않도록 안내한다. 장소 입력 여부와 관계없이 해당 카테고리에 사진이 있으면 적용하며 API 모드는 변경하지 않는다.

사물의 존재·특징·확인 가능한 부재를 감상의 근거로 연결하며, 부재가 장점으로 작용하는 경우도 다룬다. ‘있어서 좋았다/없어서 좋았다’는 문형 지시가 아니므로 그대로 반복하지 않는다. 좋다·나쁘다에 한정하지 않고 인상·분위기·만족감·아쉬움과 그 이유를 다양한 문장으로 풀어 쓴다.

수동 모드에서 맛집·카페·여행 카테고리에 장소를 입력하면, 외부 AI에 장소 검색·지역/주소/지점 대조와 다른 리뷰 참고를 요청한다. 리뷰는 메뉴·분위기·특징을 보완하는 자료로 사용하며 사용자 요청과 예시 스타일을 유지해 새 문장으로 작성한다. 문장 복제·미확인 사실·타인의 경험을 본인 경험으로 옮기는 것은 금지한다. 장소가 모호하거나 검색을 사용할 수 없다면 외부 AI가 사용자에게 추가 정보나 참고 리뷰 내용을 요청하도록 한다. 우리 서버는 검색·크롤링을 실행하지 않으며 실제 조회 여부는 사용 중인 외부 AI의 기능·실행 결과에 달려 있다. API 모드 프롬프트는 변경하지 않는다.

완성 글은 작성자 관점의 자연스러운 1인칭 방문 후기체를 사용한다. ‘공개 후기에서도’·‘실제 후기에서도’·‘사례를 찾아볼 수 있음’ 등 검색·리뷰 소개 문구는 본문에 넣지 않는다. 확인된 장소·메뉴 정보를 사용자 스타일로 풀어 쓰고, 사용자가 제공한 실제 경험을 자연스럽게 연결한다. 근거 없는 개인 평가는 출처 소개로 채우지 않고 생략하며, 구체적인 방문 사건이나 맛본 감각을 만들어 넣지 않는다.

요청 준비는 인증된 `POST /api/posts`의 `isDraft: true`로 저장하고 `GET /api/posts/[id]`의 이미지 ID를 사용한다. 임시저장 후 이미지 ID를 정하므로 응답과 원본 사진의 연결이 유지된다. 준비 후 입력값이 바뀌면 이전 준비 상태로 가져오기를 실행하지 않고 요청을 다시 준비한다.

## 결과 가져오기 API

`POST /api/posts/[id]/import`는 기존 사용자 인증 방식으로 `{ "responseText": "AI가 반환한 전체 JSON" }`을 받는다. 사용자 소유의 `DRAFT` 글만 변경할 수 있다.

버전 1 문서는 `{ version: 1, title, blocks }`를 사용한다. 문단은 `{ type: "paragraph", segments }`, 구간은 `{ text, bold?, underline?, color? }`, 이미지는 `{ type: "image", imageId }`다. 허용 색상은 기존 문서 계약의 네 가지 색상으로 제한한다. 빈 줄은 빈 문단으로 표현하고 네이버 내부 HTML·ID는 받지 않는다.

JSON 코드 블록을 제거한 뒤 전체 JSON을 파싱하고 기존 문서 검증기를 적용한다. 모든 저장 이미지 ID가 정확히 한 번 참조되어야 하며 알 수 없는 ID·중복·누락은 거부한다. 잘린 JSON, 지원하지 않는 버전·서식 등도 오류로 알린다. 실패 시 임시저장을 덮어쓰지 않는다.

성공하면 검증된 `document`, 문서 제목, 호환용 일반 텍스트 본문을 저장하고 `COMPLETED`로 변경한다. 완료된 문서는 기존 미리보기·저장 내역·확장 프로그램 흐름을 사용한다. 기존 API 생성 글도 계속 조회·전송할 수 있다.

## 검증과 배포 기준

- 기본 모드에서 키 없이 요청을 준비하고 AI API 호출 없이 임시저장할 수 있어야 한다.
- 정상 JSON·코드 블록·파일 가져오기와 빈 줄·혼합 서식·이미지 순서를 확인한다.
- 파싱 오류·이미지 ID 불일치·타인 글·완료 글 가져오기를 거부하고 기존 데이터를 보존한다.
- 요청 준비 후 입력 변경을 감지해 다시 준비하도록 안내한다. API 모드 버튼은 비활성화한다.
- 기존 저장 글의 미리보기·확장 프로그램 전송 회귀를 확인한다. 실제 네이버 입력·임시저장 후 재열기는 별도로 검증한다.

기존 `BlogPost.document` 마이그레이션은 필요하지만 이 모드를 위한 새 테이블이나 컬럼은 없다. 웹만 업데이트하며 확장 프로그램 런타임·ZIP은 변경하지 않는다. Supabase 인증·환경 설정은 계속 필요하다. 실제 실행한 테스트와 브라우저 검증 범위는 구현 완료 보고에서 별도로 기록한다.
